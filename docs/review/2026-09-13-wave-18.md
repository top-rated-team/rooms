# Wave 18, reviewed: the session was a good one, and it could be aimed at anybody

`room-account` landed 1,500 lines of session, account and sign-in code with a
green suite. Six lenses read it and three skeptics tried to refute every claim
each lens made: 27 claims, 7 confirmed by all three, 3 split, 17 refuted.

One caveat on that arithmetic, since it would otherwise read as a cleaner bill
than it is: the fixing ran while the verifying did, so several refutations are
skeptics reading code I had already repaired and quoting the comment I had just
written back at the claim. The hydration race below is the clearest case — it
was found by four separate lenses, fixed, and then refuted by nine verifiers on
the strength of the fix. Refuted does not mean it was never there.

## The hole

**A signed-in visitor could be handed somebody else's LinkedIn identity by
clicking a link.** `/api/session/linkedin?ticket=…` was a state-changing GET.
The ticket chose the identity; the cookie the browser happened to be carrying
chose the account. SameSite=Lax sends that cookie on a top-level navigation —
which is what clicking a link is — so an attacker who completed LinkedIn
themselves, kept the callback's ticket and mailed it to a signed-in person had
their own LinkedIn welded onto that person's account. They then signed in as
themselves and were inside the victim's rooms, whose addresses are the
credential. One agent ran it end to end and watched the victim's account absorb
`linkedin:mallory`.

Nothing bound the flow to a browser: the OAuth `state` lived in a server-global
map with no paired cookie, which is login-CSRF in the textbook sense.

Fixed by making the state a cookie as well as a parameter. It is written when
the flow starts and read when it returns, so a return can only be completed by
the browser that began it — and the check runs before the code is exchanged, so
a refused return does not even spend it. A return that fails it gets its own
line rather than one of the five it used to share.

## The rest, in the order they matter

**The WhatsApp sign-in code was read, never spent.** It buys a ten-year
session, and it has been on the visitor's screen, inside a QR and inside a
WhatsApp chat. It is now spent on first use, and the test proves a second claim
fails. This is the third time this repository has made a broadcast value a
durable credential; wave 17 was the last.

**The store said it was hydrated before it was.** `hydrated = true` sat in the
first read's `finally`, while accounts, identities and sessions were still on
the wire. A request arriving in that window took the early return and read
empty maps: a valid session came back signed-out, and a sign-in would have
minted a second account for an identity the database already owned. Render
restarts several times a day, so that window opens several times a day. One
flag now, set once, after both reads.

**"Rotated on every sign-in" was half true.** A new row was written; the old
one stayed valid for its full ten years. A cookie copied off a shared machine
outlived every later sign-in and every sign-out but the one performed with that
exact value. The replaced token is now ended. The account's other sessions are
its other devices and are left alone.

**The refusal handed over what it refused.** When a WhatsApp identity already
belonged to another account, the 409 said so and returned that account's room
tokens in the same body. It returns none now.

**A refused attach left an unreachable account behind** and told the person the
identity belonged to somebody else — who, in that race, was themselves. The
identity is claimed first now, under an id that has no row yet; losing the race
signs them into the account that won it.

**A successful sign-in was served as HTTP 404** carrying a meta-refresh, and the
branch that used to land a visitor in their room had become unreachable —
including `loginPickerPage`, which answered "no room is bound" to somebody who
had rooms. The callback redirects properly now and the lying function is gone.

**LinkedIn was offered on every host.** It returns to one address, the one
registered on the app. On any other host the button starts a sign-in that
finishes on a domain the visitor never asked about — and, now that the state is
bound to a cookie, fails outright. It is offered only where it returns to, and
named as belonging there otherwise. This is a live answer for wave 21:
adgrant.ai wants its own LinkedIn app, not a branch here.

**Signing out left the rooms signing in had deposited.** The owner's rule is
that sign-out must not forget the rooms — it was written before sign-in started
depositing every room on the account into localStorage. Sign-out now takes back
exactly what the session put there and leaves everything the browser knew
before it.

**The third way in did not exist.** The brief says "a person signed in by
email", and opening a mailed link signed nobody in: `attached.email` could never
be true and `whoAmI` skipped email rooms without saying why. Opening the link
proves possession of the address, which is the whole point of mailing it, so it
now signs in the way the other two do. A refusal never holds up the room — the
link is valid and it was addressed to them.

**The QR fix reached one of four copies.** The owner asked for the white plate
and no-QR-on-a-phone in the sign-in panel, and that is where it landed. The
same QR is also drawn on adgrant.ai's identify step and twice inside rooms, and
in those three it is still `text-foreground` on the page's own ground — which
in the dark theme is pale modules on near-black, a photographic negative that
no scanner will read. `server/waha.ts` emits the dark modules only and supplies
no ground of its own, so the page's ground is the QR's ground. There is one
component now, `client/src/components/WhatsAppQr.tsx`, and all four call it.

## Open, and not fixed here

**The live database is missing seven of the fifteen tables the schema
declares.** `accounts`, `sessions`, `account_identities`, `bookings`,
`room_access_links`, `room_address_bindings`, `adgrant_generations`. Nobody has
run `npm run db:push` since the schema grew. `DATABASE_URL` is set, so the code
writes, fails, logs and carries on in memory — which means every booking's
return link, every mailed room link, every address binding and now every
session dies at the next redeploy. Wave 17's whole repair is inert on the live
site for this reason. The DDL is additive and ready; running it needs the
owner's go-ahead.

**LinkedIn hand-off tickets live in a process-local Map.** Fifteen minutes, one
process. A redeploy in the middle of a sign-in drops one and the visitor is
told, honestly, that this return is not one we started. Left as it is.
