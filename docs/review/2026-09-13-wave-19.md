# Wave 19, reviewed: a finished feature with no way in

`visitor-calendar` built the whole server side of connecting a visitor's own
Google Calendar — the OAuth flow, the free/busy query, the overlay on the slot
grid, the disconnect, the privacy copy — and shipped it with 14 tests, all
green. Five lenses read it; three skeptics tried to refute every claim.

## The one that matters

**Nothing in `client/` referenced any of it.** Not one line. `parseSlotsPayload`
built its result from `timezone`, `slotMinutes` and `days` and dropped the
`visitorCalendar` field on the floor; `parseDays` did the same to
`visitorBusy`; and `BookingDialog.tsx` contained the string "visitor" zero
times. The API answered correctly and no visitor could ever have reached it.
The owner has asked for this four times, and after the wave that built it he
would have opened Book a call and seen exactly what he saw before.

Why: the parcel's `owns` list named `server/booking/*` and
`client/src/pages/privacy.tsx`, and the picker lives in
`client/src/components/site/BookingDialog.tsx`, which it did not own. The agent
respected its boundary, which is the harness working. The boundary was drawn
wrong, by me, when I wrote the parcel.

Wired now: the parser carries both fields, the picker marks busy times with a
dashed border and a line saying you can still pick one, and there is a row
under the grid that connects or disconnects. `?visitor_cal` on the return
reopens the popup — without that, a person who has just granted a Google
permission comes back to a page with no popup on it and concludes the
permission failed.

## The rest

**The OAuth state was a server-global nonce again.** Four lenses found it, and
it is the same shape the wave before this one shipped and had fixed: nothing
bound the flow to the browser that started it, so a return could be completed
by any browser. Here the prize is smaller than an account — a picker filtered
by a stranger's calendar, with a stranger's token behind the cookie — but the
fix is the same four lines, and the flows now match each other on purpose.
The state is a cookie as well as a parameter, and it is checked before the
code is exchanged, so a refused return does not spend it either.

**An error inside a 200 read as a week with nothing in it.** `freeBusy.query`
answers HTTP 200 with a per-calendar `errors` array for `notFound`, and for a
calendar the grant does not cover. The parser looked only at `busy`, found no
array, and returned `[]` — "you are free all week" — while the picker went on
saying the calendar was connected. An unreadable calendar is now no overlay
rather than an empty one.

**Expiry forgot the token instead of handing it back.** The privacy page says
the connection ends when you confirm or after five minutes. Dropping our row
ends it on our side and leaves the grant sitting in the visitor's Google
account. Expiry now revokes, best effort and never awaited.

**Every failure looked exactly like success.** Denied consent, a stale return
and a refusal from Google all produced the identical redirect, so the popup
reopened looking as it does when a calendar IS connected and said nothing.
The return now carries whether it worked, and the row says so when it did not.

**The slots route became per-visitor and did not say so.** It carries one
visitor's busy times and varies by their cookie; it was the one booking route
with no `Cache-Control: no-store`. It has one now, and a `Vary: Cookie`.

**Two sentences on the privacy page were more precise than the code.** Free/busy
ranges are not kept for five minutes — they are not kept at all; what lasts is
the token that reads them. Fixed, because on that page a sentence that is only
nearly true is the defect.

## Found on the way

**`npm test` had been globbing `server/**` only.** Two test files were never
run by the gate: `client/src/lib/booking.test.ts`, and
`scripts/build-adgrant.test.ts` — the one that guards the AdGrant library
against a refetch putting back the six wrong statements and the unsourced
percentages. That file even carried a comment calling the one-line fix "a
handoff, not this parcel's", and nobody picked the handoff up. Its pinned page
count had rotted from 23 to 27 in the meantime, which is exactly what a test
nobody runs does. The glob now covers `shared`, `client` and `scripts`; the
count is a floor with a reason written next to it; the gate went from 604
tests to 635.

## Open

**The redirect URI has to be registered on the free/busy app.** The flow sends
Google `https://top-rated.team/api/booking/calendar/callback`. If that exact
address is not in that app's Authorized redirect URIs, the connection dies at
Google's own screen with `redirect_uri_mismatch` and nothing on our side can
report it. Cannot be checked from outside the console.

**A fork's privacy page.** `/privacy` describes this connection in the present
tense unconditionally. It is written as top-rated.team's own page — it says so
in its first line, and it describes LinkedIn and WhatsApp the same way — so
this is not new, but it is one more reason adgrant.ai needs its own, which is
wave 21's item.
