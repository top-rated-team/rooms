# The rooms, read against the two questions

## 1. Talking to a room from your own WhatsApp, Slack, or Chatwoot

**It is built, and it does not survive a deploy.**

`server/bridge/` is 2,551 lines and further along than the question assumes.
Four kinds — `whatsapp`, `chatwoot`, `slack`, `clickup` — connect and
disconnect through one route; inbound from each is accepted, attributed and
fanned out into the room; an agent turn raised from a bridge claims against
`server/spend.ts` like any other. The attribution problem the README calls the
whole parcel — one number and one inbox carrying Dan, every contractor and
every agent, with the client seeing a single sender — is solved in
`attribution.ts`, with tests.

What is missing is the boring half:

```
const byWorkspace = new Map<string, Map<BridgeKind, StoredBridge>>();
```

There is no table. A connected WhatsApp group, a connected Slack, a connected
Chatwoot inbox all live in one process's memory, and this service redeploys
several times a day. Every connection dies silently at the next deploy, and
nothing tells anybody — the room simply stops being reachable from outside.

This is the fourth time this exact shape has appeared here: room bindings,
bookings, sessions, and now bridges. The other three have tables. The file's
own comment says why this one does not — "this parcel does not own
shared/schema.ts" — which is the harness working as designed and the handoff
never being picked up.

**Done, 17 September 2026.** `room_bridges` exists, in the schema and on the
live database: write-through on connect and disconnect, hydrate on boot, and
the memory maps kept as a cache — the same shape `server/identity-store.ts`
uses. A deployment with no database still bridges; it just forgets on restart,
and says so once in the boot log rather than silently.

The secret is stored rather than hashed, and the table says why: a ChatWoot
token is replayed on every outbound message, so a one-way hash would be a
connection that works until the next restart — the exact bug the table exists
to end. It is never sent to a browser.

## 2. Agents working together, and agents somebody else brings

**Neither exists, and the front page claimed both.** Corrected in the same
commit as this note.

**One message triggers at most one agent turn.** `resolveAgent` in
`server/routes.ts` reads the mentions, takes the first that resolves to an
agent, and returns it. `runAgentReply` writes the answer with
`authorKind: "agent"` and does not go back through the resolver. An agent's
message therefore never wakes another agent.

Worse than absent, there is a mix-up waiting in the history: `buildHistory`
maps every message to `assistant` if its author is an agent — *any* agent. So
an agent reading a channel where another agent has spoken sees those words as
its own earlier turns. Agent-to-agent collaboration built on this history
without changing it would produce an agent arguing with itself in someone
else's voice.

**A third-party agent cannot be admitted.** `POST /api/workspaces/:token/members`
resolves the key against `EXPERT_BY_KEY` and `EXPERTS` and answers
`Unknown expert: <key>` for anything else. Our own people only — not even our
own agents go through that route, and there is no server side at all for
somebody else's.

**What it needs**, and these are two different products:

*Agents collaborating* is mostly a history and turn-taking problem, not a model
problem. Each message needs an author identity the model can see, and a rule
for when one agent's answer may address another.

AND THE OWNER'S RULE, WHICH DECIDES THE SHAPE: "the budget runs out" is not an
acceptable stopping condition. A person must be ASKED before two agents start
answering each other, told what it will cost, and told that it needs automatic
charging — which means a card on file. So an exchange between agents is a thing
somebody starts deliberately, with a ceiling they have seen, and not something a
mention can begin by accident. `server/spend.ts` stays the last line, not the
first: a limit that is reached is already a bill somebody did not expect.

*Somebody else's agent* is an integration surface: a way to register an
endpoint or a key, a turn protocol, an identity on the member list, and the
same spend ceiling. It is the larger of the two and the one with a security
edge — an admitted agent is a member that can read the room.
